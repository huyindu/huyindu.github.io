RAGFlow 使用入门教程：开源 RAG 引擎从部署到知识库构建

为什么选 RAGFlow

2025 年上半年试了两个 RAG 方案：Dify 和 RAGFlow。Dify 的生态更成熟，工作流编排很灵活，但文档解析这块，RAGFlow 确实做得更细。尤其是 PDF 里嵌表格、图文混排这种场景，Dify 经常把表格拆得七零八落，RAGFlow 的 DeepDoc 引擎能保留表格结构，甚至能识别图片里的文字。

我用过两者的知识库构建功能后，发现一个有意思的差别：同样丢进去 50 份技术文档，RAGFlow 的检索命中率明显更高。不是因为模型好，而是它的 chunk 策略更聪明——它不是按固定长度切，而是按文档的"语义边界"来切。一个技术方案的描述不会被拦腰截断到两个 chunk 里。

RAGFlow v0.19 在 2025 年 6 月发布，这一版对文档类型支持做了大幅扩展。之前主要支持 PDF、Word、Markdown，v0.19 加上了 Excel 表格的智能解析和扫描件 OCR 的增强。部署门槛也降低了不少，下面直接从部署开始。

Docker 部署

RAGFlow 官方推荐 Docker Compose 部署。先确认机器配置：至少 4 核 CPU、16GB 内存。低于这个配置也能跑，但索引构建会很慢。

拉取代码并进入目录：

git clone https://github.com/infiniflow/ragflow.git
cd ragflow/docker
git checkout v0.19.0

调整 docker-compose.yml 里的关键配置。默认用的是内置 ES，数据量大的话建议外挂独立 ES 实例。还有一处容易忽略：RAGFlow.conf 里的 max_chunk_size，默认 512，我改成了 768——对于中文技术文档，512 token 往往切得太碎，768 的 chunk 在检索时召回率和精度平衡更好。

启动服务：

docker compose up -d

等几分钟，访问 http://服务器IP:80 就能看到登录页。首次需要注册管理员账号。v0.19 把初始化流程做得更友好了，注册完直接进向导引导你配置第一个知识库。

知识库构建

文档上传与解析

RAGFlow 的文档上传支持拖拽，一次可以传 50 个文件。上传后它会自动解析，进度条实时显示。这里有几个坑：

第一，扫描版 PDF 必须选 OCR 模式，不然解析出来是空的。v0.19 的 OCR 支持中英文混合识别，准确率比旧版高不少，但速度慢，一个 100 页的扫描件大概要 3-5 分钟。

第二，Excel 文件上传后，RAGFlow 会把每个 sheet 拆成独立文档。如果你的 Excel 里多个 sheet 之间有引用关系，解析后会丢关联。我现在的做法是把多 sheet 的 Excel 先导出成单个 CSV 再上传。

第三，图片文件（PNG、JPG）上传后会走 OCR + 描述生成双通道，但描述的质量依赖你配置的模型。我用 Qwen-VL-Max 做图片描述，效果比默认的便宜模型好得多。

Chunk 策略配置

这是 RAGFlow 最核心的配置。进入知识库设置页面，有四种切分模式：

  • General：通用模式，按 token 数固定切分。适合纯文本。
  • Q&A：识别文档中的问答对，按问答边界切。
  • Manual：手动指定分隔符。
  • Knowledge Graph：v0.19 新增，自动抽取实体和关系构建知识图谱。

实际用下来，技术文档选 General 模式配 768 token 的 chunk size、128 token 的 overlap 最稳。Knowledge Graph 模式看着高级，但对中文的实体识别准确率一般，容易把"Redis 缓存"和"Redis"识别成两个独立实体。

另外有一个容易被忽略的设置：embedding_model。默认是 BGE-large-zh，换成 BGE-M3 后多语言文档的跨语言检索能力明显提升。如果你的文档里夹杂英文术语和代码块，BGE-M3 比 BGE-large-zh 好一截。

Embedding 模型选择

RAGFlow 支持本地模型和 API 模型。本地模型通过 Ollama 或 Xinference 接入：

ollama pull bge-m3
# 在 RAGFlow 配置里填入 http://localhost:11434

API 模型的话，直接填 API Key 就行。我用的是硅基流动的 BGE-M3 API，速度和本地 Ollama 差不多，但显存投入为零。

模型选完之后点"开始构建"，知识库就进入索引阶段。这个阶段耗时取决于文档量和模型吞吐，100 份中等长度的 PDF 大概需要 10-15 分钟。

检索与问答

知识库构建完，进入检索测试页面。输入查询，RAGFlow 会返回 Top-K 个相关 chunk，以及每个 chunk 的相似度分数。这个页面的价值在于调参——你可以直观地看到不同的检索策略返回的结果质量。

检索方式有四种：

  • 向量检索：纯语义匹配，速度快但可能漏掉精确关键词匹配
  • 全文检索：基于 ES 的关键词匹配
  • 混合检索：向量 + 全文，加权融合
  • 知识图谱：基于实体关系检索

我推荐起步用混合检索，权重设成向量 0.7、全文 0.3。纯向量检索在技术文档场景容易把"Python 的 GIL 问题"匹配到"Ruby 的 GIL"，因为它们语义相近——但加上全文检索的"Python"关键词约束就不会跑偏了。

问答部分接入 LLM 后就是一个完整的 RAG 系统。RAGFlow 内置了对话界面，也提供了 API：

curl -X POST http://localhost/api/v1/chats \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -d '{"question": "如何配置 chunk size？", "kb_ids": ["your_kb_id"]}'

API 返回的 response 里带了引用的 chunk 来源，方便你做溯源验证。

和 Dify 的实际对比

踩过坑之后，我对这两个工具的定位有了清晰判断：

文档解析精度：RAGFlow 赢。尤其是在表格、扫描件、图文混排这些复杂场景。Dify 的文档解析更依赖外部服务（比如 Unstructured），可控性差一些。

工作流编排：Dify 赢。Dify 的可视化工作流非常适合搭建多步推理的 Agent，RAGFlow 目前只做知识库检索，没有工作流能力。

部署运维：平手。都是 Docker Compose 一把梭，RAGFlow 的资源消耗略高但可接受。

社区生态：Dify 赢。Dify 的插件市场、模板市场比 RAGFlow 丰富得多。

一个实际场景：需要处理 200 份 PDF 技术投标书，里面大量表格和扫描盖章页。Dify 解析后表格数据全乱了，RAGFlow 保留表格结构后检索"报价明细"能精准定位到具体段落。但如果后续要在检索结果上做多轮推理和外部 API 调用，Dify 的工作流编排更顺手。

我的结论：如果核心需求是"把文档吃透、检索精准"，选 RAGFlow。如果需要"检索 + 工作流编排 + 多 Agent"，选 Dify 或两者混用——用 RAGFlow 做知识库层，通过 API 接入 Dify 做编排层。

上线前的性能调优

知识库上线到生产前，几个参数值得仔细调：

rerank 模型：RAGFlow 支持在检索后加一层 rerank 重排序。我加了一个 BGE-Reranker-v2-m3，检索 Top-20 后 rerank 到 Top-5，召回精度提升了约 15%。代价是每次查询多了 200ms 延迟。

检索片段数 Top-K：默认是 6，可以根据文档类型调整。FAQ 类文档设 3 就够了，长篇技术文档设 8-10。设太高会塞给 LLM 太多噪音反而降低答案质量。

相似度阈值：默认 0.2，低于这个分数的 chunk 直接过滤。我设的 0.35，因为低于 0.35 的匹配基本都是噪音。

监控方面，RAGFlow 内置了一个简单的 dashboard，能看到索引状态、查询 QPS、延迟分布。建议接一个外部监控，比如 Prometheus + Grafana，RAGFlow 暴露了 metrics 端点。

最后一个提醒：v0.19 的 Knowledge Graph 功能目前还不够稳定，构建大文档量知识图谱时偶有 OOM。如果文档量超过 500 份，建议先关掉这个功能，等后续版本优化。
