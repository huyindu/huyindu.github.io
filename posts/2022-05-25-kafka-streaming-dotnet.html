Kafka 在 .NET 中的流式消息处理

从 RabbitMQ 切到 Kafka

用户行为日志系统上线一年，日活从 5 万涨到 80 万，每人每天平均产生 200 条行为事件。高峰时段每秒涌入 4000 条消息，RabbitMQ 开始出现背压——publisher confirm 耗时从 2ms 飘到 200ms，channel 被阻塞，上游服务开始超时。

排查发现 RabbitMQ 的瓶颈在流控。RabbitMQ 基于信用的流控机制在高吞吐下频繁触发，channel 进入 flow 状态暂停收发。这不是 RabbitMQ 的缺陷，是它设计场景的问题——RabbitMQ 擅长路由复杂的业务消息，不适合海量日志的流式传输。

调研后决定切到 Kafka。Kafka 3.1 + Confluent.Kafka 1.9 + .NET 6。切换后单体 Broker 的吞吐量从 RabbitMQ 的 2 万条/秒涨到 12 万条/秒——两个量级的差距。当然这也有架构差异：RabbitMQ 做了消息路由和分发，Kafka 只是追加日志。不同工具各有适配场景。

Producer 实现

Confluent.Kafka 的 Producer 支持异步生产和交付报告：

var config = new ProducerConfig
{
    BootstrapServers = "kafka1:9092,kafka2:9092,kafka3:9092",
    Acks = Acks.All,
    EnableIdempotence = true,
    CompressionType = CompressionType.Snappy,
    LingerMs = 5,
    BatchSize = 65536
};

using var producer = new ProducerBuilder<string, string>(config)
    .SetErrorHandler((_, e) => _logger.LogError("Kafka错误: {Reason}", e.Reason))
    .Build();

几个配置项的解释：

Acks.All：生产者的确认级别。0 是不等确认，丢了拉倒。1 是 leader 确认即可。All（即 -1）是等待所有 ISR（In-Sync Replicas）确认，最安全。行为日志丢失几条也许能接受，但支付相关消息必须 Acks.All。

EnableIdempotence：开启后 Producer 给每条消息分配 PID 和序列号，Broker 检查重复。配合 Acks.All 保证单分区内 Exactly-Once。注意它不跨分区——如果消息可能发到不同分区，应用层仍需幂等。

CompressionType.Snappy：生产端压缩，消费端解压。行为日志是 JSON 文本，压缩比能达到 5:1。CPU 开销很小——Snappy 设计目标就是速度优先。LZ4 更快但压缩比略低，GZip 压缩比最高但 CPU 开销大。我用 Snappy 在速度和空间之间取平衡。

LingerMs 和 BatchSize：Kafka 的吞吐秘密在于批量。LingerMs 是生产者在发送前等待更多消息的毫秒数，BatchSize 是最大批次字节数。设 LingerMs=5 意味着消息最多延迟 5ms 但能攒一个批次，吞吐量提升显著。实时日志场景 5ms 延迟完全可接受。

异步发送：

public async Task ProduceAsync(string topic, string key, string message)
{
    var msg = new Message<string, string>
    {
        Key = key,       // user_id，保证同一用户的事件进入同一分区
        Value = message
    };

    var result = await _producer.ProduceAsync(topic, msg);

    if (result.Status != PersistenceStatus.Persisted)
        _logger.LogWarning("消息投递状态异常: {Status}, Topic: {Topic}", result.Status, topic);
}

Key 的设计很重要。Kafka 用 Key 的哈希决定消息进哪个分区。我把 user_id 作为 Key，同一个用户的所有行为事件都在一个分区里，消费时天然有序。广告归因、漏斗分析这些依赖事件顺序的场景不需要额外排序。

Consumer 和消费者组

Kafka 的消费模型是消费者组（Consumer Group）。一个 Topic 有多个分区，同一个消费者组里的消费者各自认领一部分分区——一个分区只能被组内一个消费者消费。这既是并行能力的来源，也是顺序保证的基础。

var consumerConfig = new ConsumerConfig
{
    BootstrapServers = "kafka1:9092,kafka2:9092,kafka3:9092",
    GroupId = "behavior-log-processor",
    EnableAutoCommit = false,           // 手动提交
    AutoOffsetReset = AutoOffsetReset.Earliest,
    MaxPollIntervalMs = 300000          // 处理超时 5 分钟
};

using var consumer = new ConsumerBuilder<string, string>(consumerConfig)
    .SetErrorHandler((_, e) => _logger.LogError("消费错误: {Reason}", e.Reason))
    .Build();

consumer.Subscribe("user-behavior");

while (!ct.IsCancellationRequested)
{
    var cr = consumer.Consume(ct);
    try
    {
        await ProcessBehaviorEventAsync(cr.Message);
        consumer.Commit(cr); // 处理成功后提交 offset
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "处理行为事件失败, Partition: {Partition}, Offset: {Offset}",
            cr.Partition, cr.Offset);
        // 不提交 offset，下次重新消费
    }
}
