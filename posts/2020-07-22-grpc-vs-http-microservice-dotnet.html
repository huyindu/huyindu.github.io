.NET Core 微服务中的服务间通信：gRPC vs HTTP

问题触发：HTTP 扛不住了

我们的订单服务内部有一个高频调用场景：创建订单时需要调用商品服务验证 SKU 库存和价格。用户下单高峰时段，这个调用 QPS 在 2000 左右。高峰期商品服务的 HTTP 接口 P99 延迟从平日的 15ms 飙升到 180ms，订单服务因为同步等待，整体响应时间也被拖上去。

看了监控，瓶颈不在数据库查询——商品服务的 SQL 查询只有 3ms——瓶颈在 JSON 序列化/反序列化上。一个 SKU 信息 JSON 大概 800 字节，序列化 + 反序列化两端加起来要占 12ms 左右。2000 QPS 下，单是 JSON 处理就消耗了大量 CPU。

那时 gRPC-dotnet 2.30 已经比较成熟，.NET Core 3.1 内置了 gRPC 服务模板，Protobuf 3.12 是当前稳定版。我决定做个对比测试。

对比环境搭建

测试服务：一个简单的商品查询接口，输入 SKU ID 列表（1 到 10 个），返回 SKU 的价格、库存、名称。两个版本：

HTTP 版本用 ASP.NET Core Controller：

[ApiController]
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
    [HttpPost("batch")]
    public async Task<ActionResult<List<ProductDto>>> GetBatch(
        [FromBody] List<string> skuIds)
    {
        var products = await _repo.GetByIdsAsync(skuIds);
        return Ok(products.Select(p => new ProductDto
        {
            SkuId = p.SkuId,
            Name = p.Name,
            Price = p.Price,
            Stock = p.Stock
        }).ToList());
    }
}

gRPC 版本定义 Proto 文件：

syntax = "proto3";

service ProductService {
  rpc GetBatch (GetBatchRequest) returns (GetBatchResponse);
}

message GetBatchRequest {
  repeated string sku_ids = 1;
}

message GetBatchResponse {
  repeated Product products = 1;
}

message Product {
  string sku_id = 1;
  string name = 2;
  double price = 3;
  int32 stock = 4;
}

gRPC 服务实现：

public class ProductServiceImpl : ProductService.ProductServiceBase
{
    public override async Task<GetBatchResponse> GetBatch(
        GetBatchRequest request, ServerCallContext context)
    {
        var ids = request.SkuIds.ToList();
        var products = await _repo.GetByIdsAsync(ids);
        var response = new GetBatchResponse();
        response.Products.AddRange(products.Select(p => new Product
        {
            SkuId = p.SkuId,
            Name = p.Name,
            Price = (double)p.Price,
            Stock = p.Stock
        }));
        return response;
    }
}

测试数据和压测工具

测试环境：两台 4C8G 云主机，一台跑服务端，一台跑客户端。服务端一个实例（单 Pod），数据库查询走内存缓存（排除 DB 影响）。

压测工具选了两个：Bombardier（HTTP 压测）和 ghz（gRPC 压测），并发连接数从 50 逐步加到 500，每次加压持续 60 秒。

测试四组场景：

场景说明数据量
小请求-1个SKU查单个商品响应 ~200B
中请求-5个SKU查5个商品响应 ~900B
大请求-10个SKU查10个商品响应 ~1800B
流式-20个SKU用 gRPC server streaming20条记录

序列化开销是差异的主要来源。JSON 序列化在 System.Text.Json 下已经比 Newtonsoft.Json 快不少，但和 Protobuf 比还是差了一个数量级。Protobuf 的二进制编码不需要序列化属性名（字段用数字编号替代），数值直接存二进制而非字符串，体积天然小。

HTTP/2 多路复用的红利

gRPC 基于 HTTP/2，支持单连接多路复用。500 并发下的 HTTP/1.1 方案需要维护 500 个 TCP 连接，而 gRPC 只需要少量连接。服务端的 socket 句柄和 TCP 状态开销差异巨大。测试中 HTTP/1.1 在 500 并发时出现了连接超时和端口耗尽的问题（临时端口范围限制），gRPC 完全没这个问题。

切 gRPC 的工程细节

测试数据出来后，我们把订单服务到商品服务的调用从 HTTP 切成了 gRPC。切换过程比预期顺利，但有几个工程细节要注意：

Proto 文件的管理。几个微服务共用 Proto 定义，必须统一管理。我们在一个单独的 Git 仓库里放所有 Proto 文件，CI 构建时生成对应语言的代码，打包成私有 NuGet 包。服务端和客户端都引用同一个 NuGet 包，保证接口定义一致：

<ItemGroup>
  <PackageReference Include="Grpc.AspNetCore" Version="2.30.0" />
  <PackageReference Include="Company.Protos.Product" Version="1.2.0" />
</ItemGroup>

超时和重试。HTTP 调用的超时可以设 HttpClient.Timeout，gRPC 需要在调用时传 deadline：

var response = await _productClient.GetBatchAsync(request,
    deadline: DateTime.UtcNow.AddMilliseconds(500));

不设 deadline 的话 gRPC 调用永远不超时，下游挂了调用方会一直挂着。我在生产上遗漏了这步，有一次商品服务因为数据库慢查询卡住，订单服务的 gRPC 调用全挂起，线程池耗尽。加上 deadline 之后配合重试策略才稳。

重试用 Polly：

var retryPolicy = Policy
    .Handle<RpcException>(ex => ex.StatusCode == StatusCode.Unavailable)
    .WaitAndRetryAsync(3, retryAttempt =>
        TimeSpan.FromMilliseconds(100 * Math.Pow(2, retryAttempt)));

var products = await retryPolicy.ExecuteAsync(async () =>
    await _productClient.GetBatchAsync(request, deadline: ...));

负载均衡。gRPC 连接是长连接，标准的 K8s Service (ClusterIP) 做负载均衡只在连接建立时有效——一旦建立，后续请求全走同一条连接到同一个 Pod。需要用 Headless Service + 客户端负载均衡，或者用 Service Mesh 的 sidecar 代理（比如 Linkerd）来实现真正的连接级负载均衡。我选择了在客户端用 DNS 轮询 + Subchannel 的方式：

services.AddGrpcClient<ProductService.ProductServiceClient>(o =>
{
    o.Address = new Uri("dns://product-service-headless");
}).ConfigureChannel(o =>
{
    o.Credentials = ChannelCredentials.Insecure;
    o.ServiceConfig = new ServiceConfig
    {
        LoadBalancingConfigs = { new RoundRobinConfig() }
    };
});

网关的坑。如果 API 网关还需要对外暴露 gRPC 接口（比如给移动端用），Ocelot 对 gRPC-Web 的支持有限。我当时的做法是：外部流量继续走 HTTP/JSON 通过网关，内部服务间通信走 gRPC 直连。网关对内网 gRPC 调用做转换——这个模式叫 gRPC 网关 (gRPC-Gateway)，但 .NET 生态当时没有现成的方案，我在网关层写了一层转换代码，把外部的 HTTP 请求转成 gRPC 调用。不算优雅，但能跑。

序列化性能深入对比

单独做了序列化 benchmark，用 BenchmarkDotNet 对比三种方案的序列化 + 反序列化耗时（10 个 SKU 对象）：

方案序列化反序列化总耗时消息大小
Newtonsoft.Json8.2μs12.5μs20.7μs1850B
System.Text.Json3.8μs5.1μs8.9μs1780B
Protobuf0.9μs1.2μs2.1μs520B

Protobuf 序列化速度快 4-9 倍，体积小 70%。在 10000 QPS 的场景下，这个差异直接决定了 CPU 使用率。

什么时候不该用 gRPC

gRPC 不是万能药。有几个场景我不推荐：

浏览器直连。浏览器不支持 HTTP/2 Trailers，需要 gRPC-Web 做中间代理。多一层代理就多一层复杂度。对外暴露的 API，特别是要给第三方调用的，HTTP/JSON 更实在。

调试和排查。gRPC 请求/响应是二进制，curl 没法直接测试。调试工具链（grpcurl、BloomRPC）不如 Postman 普及。我常用的调试方式是用 grpcurl：

grpcurl -plaintext -d '{"sku_ids": ["SKU001","SKU002"]}' \
  product-service:50051 ProductService/GetBatch

比 curl 多了几个参数，新同事上手慢一些。

小规模服务。如果整个系统就三四个微服务，QPS 也不高，HTTP/JSON 完全够用。引入 Protobuf 的代码生成步骤、Proto 文件管理、NuGet 包版本控制，这些工程开销在小团队里不划算。

切 gRPC 后我们的订单服务延迟下降了 60%，商品服务 CPU 从 65% 降到 25%。效果实打实，但这是建立在内部服务高 QPS 通信的前提上。
