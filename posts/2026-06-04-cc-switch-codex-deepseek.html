CC Switch 实战：把 DeepSeek 接入 Codex，在 Claude Code 中实现多视角代码审查

我在实际项目里试了一套组合：Claude Code 写代码，Codex + DeepSeek-V4 审代码。效果比预期好——DeepSeek 指出了 3 个 Claude 完全忽略的空指针风险，和一个在中文文档注释里硬编码路径的坑。换单一模型审查自己的产出，盲区是真实存在的。

这套流程能跑通，靠的是 CC Switch v3.16.0 刚加的 Chat Completions → Responses 协议转换。Codex 只认 OpenAI Responses API，而 DeepSeek、Kimi、GLM 这些国产模型说的都是 Chat Completions，以前根本接不进去。现在 CC Switch 在本地做了一层代理，帮你把两边翻译通。

核心链路：协议转换怎么做的

Codex 和国产模型之间的协议差异不只是 URL 不同，整个请求体和响应格式都是两套东西：

差异点Responses APIChat Completions API
请求路径/v1/responses/chat/completions
流式事件格式Responses SSE 事件族Chat SSE delta 事件
推理/思考内联 <think> 块reasoning_content 字段
工具调用Responses tool 结构Chat tool_calls 结构
会话续接previous_response_idmessages 数组全量携带

把 Chat 格式的 API 直接塞进 Codex 配置，结果就是 404、400、流式解析崩溃。CC Switch 的方案是启动一个本地代理（默认 127.0.0.1:15721），Codex 始终以 Responses 格式跟代理对话，代理在中间做双向转换：

Codex 发送 Responses 请求
        ↓
CC Switch 本地路由（127.0.0.1:15721）
        ↓ 请求转换：Responses → Chat Completions
第三方 DeepSeek API
        ↓ 响应转换：Chat Completions → Responses
CC Switch 本地路由
        ↓
Codex 收到标准 Responses 响应

转换过程保留了 reasoning_content、think 块、流式推理摘要、工具调用状态和 previous_response_id 续接链路。v3.16.0 还会根据上游供应商自动识别推理接口并注入正确的 thinking 参数——DeepSeek 走 thinking:{type}，Kimi 走 enable_thinking，OpenRouter 走原生 reasoning:{effort}。不需要手配，也不用担心把不支持的参数透传过去导致上游拒请求。

v3.16.0 一次性上了 22 个带 Chat 路由的 Codex 供应商预设，覆盖了几乎所有国内主流模型——智谱 GLM、Kimi、MiniMax、StepFun、百炼、SiliconFlow、火山、豆包 Seed 等。之前适配一个供应商要手写一整套协议转换代码，现在勾一下「需要本地路由映射」开关就完事。

多视角审查：这条路实际怎么走

CC Switch 同时管着 Claude Code 和 Codex 的供应商配置，切换模型不需要改配置文件——这是多视角审查能落地的前提。思路很简单：

  • Claude Code（配 Claude Opus 或 Sonnet）：主力编程，写代码、修 bug、重构
  • Codex + DeepSeek-V4（通过 CC Switch 路由）：独立审查，从不同角度审视同一段代码

操作上分三步。在 Claude Code 里完成一轮开发后，生成 diff：

git diff HEAD -- '*.py' '*.ts' '*.go' > /tmp/review-diff.patch

打开另一个终端启动 Codex（它通过 CC Switch 已经指向 DeepSeek），把 diff 丢进去：

> 审查 /tmp/review-diff.patch，从安全性、正确性、性能和可维护性四个维度给意见

审查结果带回 Claude Code，让它逐条处理。如果问题多，可以让 Claude Code 先分类——哪些是必须修的、哪些是建议优化的、哪些可以忽略——然后按优先级修复。

我在一个 2000 行的 PR 上实际跑过这套流程。Claude Code 写完代码后自审了一遍，没发现问题。Codex + DeepSeek 额外挖出了：

  • JWT payload 里直接存了用户手机号——应该只存 user_id 然后查库，手机号是敏感信息
  • 两处数据库查询没有 N+1 保护，数据量上去之后性能会崩
  • 一个测试用例的 mock 没有在 teardown 里清理，导致后续测试随机挂——这种问题 CI 上极难复现

这三个问题 Claude 自审都没提。不是我黑 Claude——任何模型审查自己的产出都有盲区。代码是你写的，审查时大脑会自动跳过那些「我知道这里没问题」的地方，而另一个模型没有这个预设。

换不同模型做审查的价值还体现在它们的知识侧重点不同。Claude 对英文社区的常见模式和 bug 模式更敏感，DeepSeek 在中文注释相关逻辑、国内常见业务场景（手机号验证、身份证格式、微信支付回调等）上判断更准。同一个 PR，两边给的建议经常不重叠——加起来才是完整的审查意见。而且这个成本很低：按 DeepSeek 的 API 定价，审查一个 2000 行的 PR 大概消耗几毛钱，比找第二个同事 review 便宜得多。

配通 DeepSeek：四步走

安装

从 GitHub Releases 下载 CC Switch（要求 ≥ 3.16.1），macOS 可以 brew install --cask cc-switch。Windows 下 .msi，Linux 下 .deb / .rpm / .AppImage。安装后打开，确认版本号 ≥ 3.16.1。

添加 DeepSeek 供应商

CC Switch 顶部切到 Codex 标签 → 右上角加号 → 选择「DeepSeek」预设。填入 API Key（sk-xxx）。预设已经自动配好了：

  • base URL：https://api.deepseek.com
  • 模型映射表：deepseek-v4-pro（128K）、v4-flash（128K）、v3-0324（128K）等
  • 「需要本地路由映射」开关：已打开（DeepSeek 是 Chat Completions 接口，必须走协议转换）

你可以把默认模型改为 deepseek-v4-pro，其他不用动，保存。预设里的模型映射表不是摆设——它决定了 Codex 的 /model 菜单里会列出哪些模型，以及每个模型的上下文窗口大小，UI 里可以直接编辑增删。修改映射表后必须重启 Codex 才能生效，因为模型目录是启动时一次性加载的。

开启本地路由接管 Codex

设置 → 路由 → 本地路由：

  1. 打开「路由总开关」，启动本地代理（默认 127.0.0.1:15721）
  2. 在「路由启用」中打开「Codex」

接管后，CC Switch 会把 Codex 的 live 配置指向 http://127.0.0.1:15721/v1，wire_api 强制保持 responses。真实的 API Key 留在 CC Switch 的供应商配置里，不会暴露到 Codex 文件。这套机制的好处是切换供应商完全在 CC Switch 层面完成——Codex 自己只知道「我在跟一个 Responses API 对话」，至于这个 API 背后是 DeepSeek 还是 Kimi，Codex 完全不关心，也不应该关心。

验证接管是否生效：

grep -A5 '\[api\]' ~/.codex/config.toml
# 应该看到 base_url = "http://127.0.0.1:15721/v1"

切换并重启

Codex 面板里启用 DeepSeek 供应商，然后重启 Codex。config.toml 和 model_catalog_json 都是启动时加载的，运行中不会热更——这是 Codex 的设计，不是 CC Switch 的问题。重启后用 /model 确认当前模型是 DeepSeek 预设里的模型，发一个 prompt 测试：

> 用 Python 写一个快速排序

在 CC Switch 用量面板里能看到请求的 token 消耗和成本，确认流量走了 DeepSeek。还可以顺手看一眼路由面板的请求数——如果数字在涨，说明链路没断。

保留官方登录态（可选）

Codex App 的手机远程操作和官方插件依赖 ~/.codex/auth.json 里的 OpenAI 登录缓存。如果直接把第三方 API Key 写进 auth.json，这些功能就没了。v3.16.1 的解决方案是：

  1. 先在 CC Switch 里切到 OpenAI Official 供应商，启动 Codex 用 OpenAI 账号登录一次（Free 订阅就行）
  2. 设置 → 通用 → Codex 应用增强 → 打开「切换第三方时保留官方登录」
  3. 切回 DeepSeek，重启 Codex

开启后，CC Switch 的切换逻辑只写 config.toml（管模型供应商和 API Key），不动 auth.json（管官方登录态）。Codex App 仍然认为你是官方账号，但实际模型请求走的是 DeepSeek。这个方案的代价是 Codex 界面里的账号显示始终是官方账号，你没法从 UI 上直接看出当前用的是哪个供应商的模型——需要到 CC Switch 的用量面板或请求日志里确认。

如果你不需要手机远程操作和官方插件，这一节可以跳过。直接把「保留官方登录」关掉，CC Switch 会走兼容旧版本的写入路径，第三方 API Key 直接写进 auth.json。两种方式在模型流量上没区别，区别只在于 Codex App 侧的功能可用性。

注意：Codex App 里显示的账号始终是官方账号，不代表流量还在走 OpenAI。实际供应商以 CC Switch 当前选中为准，可以在用量面板或请求日志里确认。

踩过的坑

三个最容易卡住的地方：

Codex 报 404。 几乎都是没开 Codex 接管。检查 ~/.codex/config.toml 的 base_url 是不是指向 127.0.0.1:15721/v1，同时确认本地路由的 Codex 开关已打开。另外如果你用的是自定义供应商而非预设，注意 base URL 是服务根地址（如 https://api.deepseek.com），不要带 /v1 后缀或 /chat/completions 路径——路由层会自动补。

/model 菜单看不到 DeepSeek 模型。 必须重启 Codex。模型目录是启动时加载的，这跟 CC Switch 的接管状态无关。

流式响应异常或 token 统计为 0。 确认供应商表单里「需要本地路由映射」已打开。这个开关控制的是是否做 Chat → Responses 转换——关了就等于把 Chat 接口直接暴露给只认 Responses 的 Codex，流式事件当然对不上。如果你用的是中转站或者聚合平台（OpenRouter、SiliconFlow 等），同样要确认 API 格式选的是 Chat Completions 并开了路由映射。
