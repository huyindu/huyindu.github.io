多租户 SaaS 数据隔离方案对比

为什么纠结

给一个企业级 SaaS 做技术选型的时候，数据隔离方案我纠结了很久。三种主流方案——独立数据库、共享数据库独立 Schema、共享表——各有各的坑，不是简单"选个最安全的"就能收工。当时那套系统用 .NET 6 和 PostgreSQL 14，EF Core 6.0 刚出了 DbContextFactory 和 Compiled Models，给共享表方案加了不少底气。最后选了共享表+租户ID列，理由和踩坑过程如下。

方案一：独立数据库——贵但最安全

每个租户一个 PostgreSQL database。Schema 完全一样，只是物理隔离。

优点很直白：隔离级别最高，一个租户的查询再烂也拖不垮别人；数据备份和恢复可以按租户粒度操作；大客户审计要求能轻松满足。缺点也直白：贵。每个 database 都有固定开销，租户数上去了运维成本线性增长。迁移（EF Core migration）要跑 N 次。连接池管理麻烦——每个租户一个连接字符串，连接数可能爆炸。

实现上，需要维护一个租户到连接字符串的映射表（租户元数据库），每次请求根据租户标识查映射，动态构造 DbContext。EF Core 6 的 DbContextFactory 能帮忙管理生命周期，但解决不了连接数问题。

方案二：共享数据库独立 Schema——折中但运维复杂

所有租户共用一个 database，但每个租户有自己的 schema（PostgreSQL namespace）。表名一样，路径不同：tenant_a.orders、tenant_b.orders。

隔离级别介于独立库和共享表之间。PostgreSQL 的 schema 天然有权限边界，可以限制租户 A 无法访问租户 B 的表。迁移可以批量跑（遍历所有 schema 执行同一套 migration）。

坑在运维：PostgreSQL 默认的 search_path 是 "$user", public，每次查询都要 set search_path 或者用完全限定表名。EF Core 对动态 schema 的支持很弱——表名映射在 OnModelCreating 里就定死了，要动态切换得用拦截器劫持 SQL 把表名替换掉，或者每个租户创建一个 Model。另一个坑是 schema 数量上限：几百个租户还好，几千个租户之后 pg_catalog 膨胀得厉害，\dn 都会卡。

方案三：共享表+租户ID列——简单但有隐形成本

所有租户的数据存在同一张表里，靠一个 tenant_id 列区分。我最终选的就是这个。

核心实现就两步。第一步，所有实体实现一个接口：

public interface ITenantEntity
{
    Guid TenantId { get; set; }
}

public class Order : ITenantEntity
{
    public Guid Id { get; set; }
    public Guid TenantId { get; set; }
    public decimal Amount { get; set; }
}

第二步，EF Core 的全局查询过滤器：

protected override void OnModelCreating(ModelBuilder builder)
{
    foreach (var entity in builder.Model.GetEntityTypes()
        .Where(e => typeof(ITenantEntity).IsAssignableFrom(e.ClrType)))
    {
        builder.Entity(entity.ClrType)
            .HasQueryFilter(e => EF.Property<Guid>(e, "TenantId") == _tenantId);
    }
}

_tenantId 从当前请求上下文注入。配合 EF Core 6 的 DbContextFactory，每个请求创建独立的 DbContext 实例，_tenantId 天然隔离。

索引设计是重头戏。所有查询都带 WHERE tenant_id = @p0，所以租户 ID 必须放在复合索引最左边：

CREATE INDEX idx_orders_tenant_created 
ON orders (tenant_id, created_at DESC);

不这么建的话，tenant_id 过滤走不上索引，全表扫描能把你数据库打穿。

隐形成本：数据量、误操作、大租户

共享表最大的风险不在技术上，在人的失误上。写 SQL 忘了加 WHERE tenant_id，UPDATE 刷了全表——这种事故我在测试环境亲手制造过一次，好在测试环境数据少且是假的。

防御措施：一，EF Core 的查询过滤器已经是强制性的，除非显式调用 IgnoreQueryFilters()；二，用 PostgreSQL 的 RLS（Row Level Security）做数据库层面的最后防线：

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON orders
    USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

每次连接开始时执行 SET app.current_tenant_id = '<tenant-id>'，PG 在内核层面拒绝跨租户访问。双重保险。

另一个问题是"大租户效应"。一个租户数据量是其他租户的 100 倍，它的查询会拖慢整张表。我的缓解策略：表分区（按 tenant_id 哈希分区），PostgreSQL 14 的原生分区表性能已经足够好；对超大租户单独建表空间放到 SSD 上；业务层对大租户的批量查询做限流。

迁移策略

我用过独立库和共享表两种模式，迁移体验天差地别。独立库时，一个 migration 要跑 N 遍（N=租户数），CI 里跑一次 migration 脚本要十几分钟。共享表方案只跑一次，CI 一分钟结束。

共享表的 migration 唯一要注意的是：加非空列必须给默认值，否则已有租户的数据行会炸。常用套路：

migrationBuilder.AddColumn<string>(
    name: "NewColumn",
    table: "Orders",
    nullable: true,
    defaultValue: "placeholder"
);
// 之后再来一个 migration 改成 nullable: false

选型决策框架

我推荐按租户数量和安全要求组合决策：

  • 租户 < 100 且安全要求高 → 独立数据库
  • 租户 100 ~ 1000 且安全要求高 → 独立 Schema
  • 租户 > 1000 或安全要求一般 → 共享表 + 租户ID列

我的场景是几百个中小租户，安全要求中等（不是金融/医疗），共享表+RLS 的组合最划算。

发现：EF Core 6 的两个关键特性

DbContextFactory 让每次请求创建新的 DbContext 变得非常干净，配合 AddDbContextFactory 注册，构造函数直接注入：

public class OrderService
{
    private readonly IDbContextFactory<AppDbContext> _factory;
    
    public async Task<List<Order>> GetOrdersAsync()
    {
        await using var ctx = await _factory.CreateDbContextAsync();
        return await ctx.Orders.ToListAsync();
    }
}

Compiled Models 对大租户的冷启动有帮助。正常 EF Core 第一次查询要编译模型，大模型可能卡一两秒。用 dotnet ef dbcontext optimize 生成预编译模型之后，首次查询下降到几十毫秒。

我的最终架构：tenant_id 通过 JWT claim 传递，中间件解析后注入 scoped 服务，DbContextFactory 从 scoped 服务取租户 ID 创建 DbContext。RLS 作为额外保险。索引全部以 tenant_id 开头。这套跑了半年，经历过一次大租户的促销流量高峰，PostgreSQL 14 的哈希分区把热点数据分散得挺好，查询延迟没明显上升。
