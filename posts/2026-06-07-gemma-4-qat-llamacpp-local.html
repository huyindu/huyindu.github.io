Gemma 4 QAT 本地部署：6 GB 显存跑 12B 多模态模型

在消费级显卡上跑 12B 模型，一直是个尴尬的事。BF16 需要 24 GB 显存，4-bit PTQ 量化虽然降到 7-8 GB，但回答质量打折明显——代码生成频繁出错，多轮对话跑偏率远高于原版。2026 年 6 月 5 日，Google DeepMind 放出了 Gemma 4 全系列的 QAT（Quantization-Aware Training）版本，局面彻底改变。12B 指令微调模型的 GGUF 文件只有 6.26 GB，精度接近 BF16。我在 RTX 4060 8 GB 上跑了两天，8K 上下文对话和代码生成都稳得很，显存还有 1 GB 余量。这次 Google 一次放出了 E2B、E4B、12B、26B A4B 和 31B 五个尺寸的 QAT 版本，覆盖从手机到服务器的全场景，但最让我兴奋的是 12B——它刚好是消费级显卡和高质量推理的交叉点。

Gemma 4 本身也是近期大模型发布里少有的「真开放」选手。Apache 2.0 协议，256K 上下文，原生多模态（文+图+音），外加 system prompt 和 function calling 支持。QAT 补上了最后一块短板——硬件门槛。这也是我用过的第一个能在 8 GB 卡上以接近原生精度跑起来的 12B 模型，之前试过 Qwen 2.5 14B 和 Llama 3 8B，前者爆显存，后者能力不够。Gemma 4 12B QAT 刚好卡在甜点位。

QAT 与 PTQ：本质区别

量化这件事，过去主流的 PTQ（Post-Training Quantization）是训练完成后对权重做四舍五入式压缩。llama.cpp 的 Q4_K_M 用 4-bit 存大多数权重，关键层保留更高精度。12B 这个量级，PTQ 下来质量损失不小——推理和代码任务尤其明显。

QAT 做法根本不同：训练阶段就把量化噪声喂给模型。前向传播时，权重被模拟量化为 4-bit 后再计算；反向传播时，梯度通过「直通估计器」（Straight-Through Estimator）回传到原始权重。模型在训练中就学会了补偿量化误差，最终导出的 4-bit 权重天然比 PTQ 更准确。可以理解为模型已经习惯了以 4-bit 精度思考，而不是训完被强行降级。

Unsloth 的测试数据印证了这一点。他们对比标准 PTQ Q4_0 和 Unsloth Dynamic Q4_0 在 QAT 基座上的 KL 散度：Gemma 4 E2B 的标准 Q4_0 平均 KL 散度 0.051，Unsloth 动态量化压到 0.00173——精度提升了 29 倍，文件还小了 22%。关键在于 QAT 用 BF16 做量化缩放因子，而 llama.cpp 标准 Q4_0 用 F16 做缩放，类型不匹配导致额外误差。Unsloth 的动态量化修复了这个对齐问题。

方案量化时机缩放精度KL 散度（E2B）质量
标准 PTQ Q4_0训练后F160.051明显下降
QAT BF16 → Q4_0训练中F160.008轻微下降
QAT BF16 → UD-Q4_K_XL训练中对齐 BF160.0017接近原生

我之前在几款 PTQ 量化的 7B-14B 模型之间来回切换，代码生成时的偶发性幻觉和指令遵循偏差是最头疼的问题——明明前一句还正常，下一句就跑偏到不相干的逻辑。换上 Gemma 4 QAT 后，同一组 prompt 的输出稳定性提升明显。多轮对话的上下文保持尤其稳，比同体积的 PTQ 模型强了不止一个档次。

安装 llama.cpp

llama.cpp 对 Gemma 4 架构的支持已经合入主线，安装后确保版本在 b4840 以上。推荐直接装预编译版本：

# macOS / Linux（推荐）
brew install llama.cpp

# Windows
winget install llama.cpp

没有包管理器的话，从 GitHub Releases 下载预编译二进制：

# 下载最新 Release（Linux x64 CUDA 版）
wget https://github.com/ggml-org/llama.cpp/releases/latest/download/llama-bin-linux-x64-cuda.tar.gz
tar xzf llama-bin-linux-x64-cuda.tar.gz -C ~/llama.cpp

# 国内 wget 慢可以走代理
# curl --socks5-hostname localhost:10808 -LO https://github.com/ggml-org/llama.cpp/releases/latest/download/llama-bin-linux-x64-cuda.tar.gz

如果一定要自己编译（定制后端参数）：

git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp
cmake -B build -DGGML_CUDA=ON
cmake --build build --config Release -j$(nproc)

安装完成后确认版本和 CUDA 支持：

llama-cli --version
llama-cli --help 2>&1 | grep -i cuda

下载模型

Hugging Face 上有两个社区 GGUF 发布源：

推荐 Unsloth 的 UD-Q4_K_XL——精度更好，体积更小。下载方式有三种。

方式一：huggingface-cli

pip install huggingface_hub

huggingface-cli download unsloth/gemma-4-12B-it-qat-GGUF \
  gemma-4-12B-it-qat-UD-Q4_K_XL.gguf \
  --local-dir ./models/gemma-4-12b-qat

# 需要多模态的话，mmproj 也下了
huggingface-cli download unsloth/gemma-4-12B-it-qat-GGUF \
  mmproj-F16.gguf \
  --local-dir ./models/gemma-4-12b-qat

方式二：hf-mirror.com（国内直连）

mkdir -p ./models/gemma-4-12b-qat
curl -L -o ./models/gemma-4-12b-qat/gemma-4-12B-it-qat-UD-Q4_K_XL.gguf \
  https://hf-mirror.com/unsloth/gemma-4-12B-it-qat-GGUF/resolve/main/gemma-4-12B-it-qat-UD-Q4_K_XL.gguf

方式三：llama.cpp 直接拉（零步下载）

llama-cli -hf unsloth/gemma-4-12B-it-qat-GGUF:UD-Q4_K_XL

第三种最省事——llama.cpp 自动从 HF 下载缓存，下次启动直接用缓存，不需要手动管理文件。国内网络慢的话设一下代理环境变量：export ALL_PROXY=socks5h://127.0.0.1:10808。

运行模型

终端对话

llama-cli \
  -hf unsloth/gemma-4-12B-it-qat-GGUF:UD-Q4_K_XL \
  -ngl 99 \
  -c 8192 \
  --temp 0.7 \
  -p "用中文写一个二分查找的 Python 实现，包含边界处理注释"
  • -ngl 99：99 层全卸 GPU。显存不够可以降到 30，部分层用 CPU 跑——代价是速度降 30-40%
  • -c 8192：上下文窗口。模型支持 256K，但日常开发 8K-16K 足够

如果模型已下载到本地：

llama-cli \
  -m ./models/gemma-4-12b-qat/gemma-4-12B-it-qat-UD-Q4_K_XL.gguf \
  -ngl 99 -c 8192 --temp 0.7 \
  -p "解释一下 Rust 的所有权系统"

OpenAI 兼容 API 服务

开发场景优先用 llama-server，提供完整的 /v1/chat/completions 端点，支持流式输出和 function calling：

llama-server \
  -hf unsloth/gemma-4-12B-it-qat-GGUF:UD-Q4_K_XL \
  -ngl 99 -c 8192 \
  --host 0.0.0.0 --port 8080

测试一下：

curl http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "messages": [
      {"role": "user", "content": "什么是 Transformer 的自注意力机制？"}
    ],
    "temperature": 0.7,
    "max_tokens": 512
  }'

返回格式和 OpenAI API 完全一致，可以直接对接 Continue、Open WebUI、Chatbox、ChatGPT-Next-Web 等前端工具。我日常开发把它跑在本地 8080 端口，代码补全用 Continue 接，偶尔问答用 Chatbox，体验和云端模型没区别——还不用等网络延迟。

多模态推理

Gemma 4 12B 是「Unified」架构——没有独立的视觉编码器。图像 patch 通过轻量线性层直接投影到 LLM 的 embedding 空间，整个流程在一个 decoder-only transformer 里完成。好处是推理延迟更低，而且可以一次性微调整个模型。代价是图片预处理逻辑由 mmproj 文件承担，需要额外下载。

# 下载 mmproj（如前面已下可跳过）
curl -L -o ./models/gemma-4-12b-qat/mmproj-F16.gguf \
  https://hf-mirror.com/unsloth/gemma-4-12B-it-qat-GGUF/resolve/main/mmproj-F16.gguf

# 图片推理
llama-cli \
  -m ./models/gemma-4-12b-qat/gemma-4-12B-it-qat-UD-Q4_K_XL.gguf \
  --mmproj ./models/gemma-4-12b-qat/mmproj-F16.gguf \
  -ngl 99 -c 8192 \
  -p "这张图片里有什么？详细描述" \
  --image ./screenshot.png

12B Unified 理论支持文本、图片、音频三种输入。不过音频推理在 llama.cpp 中的支持还在完善，目前图片推理是稳定的。我试了一张架构图识别，输出准确度和 Qwen-VL 7B 的 FP16 版本不相上下——考虑到体积差距，这个表现相当不错。

显存与性能实测

以下数据在 RTX 4060 8 GB + 32 GB DDR5 环境下跑出，模型为 Unsloth UD-Q4_K_XL：

上下文长度显存占用生成速度可用余量
1K~6.3 GB~45 tok/s~1.7 GB
4K~6.5 GB~42 tok/s~1.5 GB
8K~6.8 GB~38 tok/s~1.2 GB
16K~7.5 GB~34 tok/s~0.5 GB
32K~8.5 GB~28 tok/s溢出，需降 -ngl

8K 上下文日常使用绰绰有余，显存还有 1 GB 以上余量，不会被系统 OOM killer 盯上。16K 虽然能跑全 GPU，但只剩 0.5 GB 余量，系统桌面环境可能受影响——此时把 -ngl 降到 35，显存压到 6.5 GB，速度掉到 25 tok/s 左右，但稳定。我在实际使用中发现一个技巧：如果只是做代码补全，上下文设 4K 就够了，显存压在 6.5 GB 以下，长时间挂着也不会触发驱动超时。

对比一下：同样是 6-7 GB 体积，Qwen 2.5 7B Q4_K_M 大约 4.7 GB，但知识面和推理深度显然不如 12B 量级。Gemma 4 12B QAT 在这个体积下提供了接近原生 12B 的输出质量——这件事在两年前是不可想象的。两年前跑 13B 级别的模型至少需要 RTX 3090/4090 这种 24 GB 卡，现在一台入门游戏主机就能搞定。更关键的是，12B QAT 在 MMLU Pro 上拿了 77.2%，LiveCodeBench v6 拿了 72.0%，这些分数放在去年是可以跟 70B 量级的模型掰手腕的。

多 GPU 场景：

# 双卡环境下 llama.cpp 自动拆分，每卡占约 3.2 GB
llama-server \
  -m ./models/gemma-4-12b-qat/gemma-4-12B-it-qat-UD-Q4_K_XL.gguf \
  -ngl 99 -c 16384 --port 8080

如果显存实在紧张，还有一条纯 CPU 路线：关掉 GPU 卸載（不传 -ngl），12B Q4 模型在 64 GB 内存的机器上纯 CPU 跑，速度大约 8-12 tok/s。不算快，但 64 GB 内存比 24 GB 显存便宜多了。

几个踩过的坑

量化格式选错。Unsloth 的 UD-Q4_K_XL 和 LM Studio 的标准 Q4_0 不是同一个东西。前者在 QAT 基座上做了 BF16 缩放对齐，精度明显更好。如果下了 LM Studio 的版本，可以对比跑一下同一组 prompt，会发现复杂指令的遵循度有差别。我不推荐用标准 Q4_0 跑 QAT 模型——浪费了 QAT 的精度优势。

gguf 文件不兼容旧版 llama.cpp。Gemma 4 架构用了新的 tokenizer 和 attention 机制，需要 llama.cpp b4840 以上版本。如果你本机装过旧版，务必 brew upgrade llama.cpp 或重新下载最新 Release。我遇到过用旧版加载新 gguf 直接 segfault 的情况，排查了半天才发现是版本问题。

mmproj 版本要对齐。多模态推理时，mmproj 必须和主模型文件来自同一个 repo。不要从 Unsloth 下 GGUF 却用了 LM Studio 的 mmproj，投影矩阵不匹配会导致图片识别完全错误。Unsloth 的 repo 提供了 BF16、F16、F32 三种 mmproj，日常使用 F16 就够——质量和 F32 没差别，体积小一半。

国内 Hugging Face 直连下载。hf-mirror.com 的同步有 1-2 天延迟。如果模型刚发布急着用，可以走代理下载：export HF_ENDPOINT=https://hf-mirror.com 给 huggingface-cli 全局切镜像，或者单独对 curl 加 --socks5-hostname localhost:10808。

Google 这次在 Gemma 4 上同步放出 QAT 权重，信号明显：大模型本地部署的硬件门槛在快速下探。12B 级模型过去需要专业卡或云端推理，现在几千块的消费级显卡就能跑，而且质量不打折。llama.cpp 的 Vulkan 后端还覆盖了 AMD 和 Intel 显卡，本地 AI 的能力边界还在外扩。下一步期待的，是 QAT 成为新模型的标配——训出来就自带量化版本，而不是让社区再跑一次 PTQ。
