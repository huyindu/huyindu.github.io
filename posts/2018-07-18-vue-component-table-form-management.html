Vue 组件化实战：后台管理系统的表格与表单封装

场景：表单的"复制粘贴"地狱

项目做到第四个模块的时候，我有八个页面各有一张表单。每张表单结构不一样——字段不同、校验规则不同、布局也有差异——但外层逻辑高度重复：打开弹窗、绑定数据、提交前校验、关闭时清空、提交 loading 状态、错误提示。八个页面的八个表单，代码加起来超过 3000 行，其中 70% 是重复的模板和逻辑。

改一个通用行为——比如全局把提交按钮从右对齐改成居中——要改八个地方。这种事一多，迟早改漏一个。所以必须得把表单抽象成组件。

设计思路：配置驱动 vs 插槽自由

有两种极端。一种是全配置驱动：传一个 JSON 描述字段列表，组件内部根据配置 v-for 渲染所有表单项。好处是复用性极强，缺点是复杂交互（比如联动下拉、自定义字段排列）需要去组件内部写 case，变成配置的配置，可读性崩坏。

另一种是壳子组件+默认插槽：只提供表单容器（弹窗、loading、按钮区），字段完全由父组件用插槽填充。灵活性最高，但每个页面仍然要手写所有字段的 el-form-item，外层逻辑照样重复。

我折中了一下：字段用配置渲染，但预留插槽给特殊字段；增/改共用一个组件，由 mode prop 区分。

表单组件的 props 设计

props: {
  // 表单字段配置数组
  fields: {
    type: Array,
    required: true
    // 每个 field 对象: { prop, label, type, rules, options, disabled, span }
  },
  // 模式: 'create' | 'edit'
  mode: {
    type: String,
    default: 'create',
    validator: v => ['create', 'edit'].includes(v)
  },
  // 编辑时的回填数据
  formData: {
    type: Object,
    default: () => ({})
  },
  // 弹窗可见性
  visible: {
    type: Boolean,
    default: false
  }
}

字段 type 支持 input、select、datepicker、switch、textarea、upload 六种。对多数后台表单来说够用。遇到不够用的——比如需要级联选择器——加一个 custom 类型，渲染时走具名插槽：

<template v-for="field in fields">
  <el-form-item
    v-if="field.type !== 'custom'"
    :key="field.prop"
    :label="field.label"
    :prop="field.prop"
    :rules="field.rules"
  >
    <el-input
      v-if="field.type === 'input'"
      v-model="localForm[field.prop]"
      :disabled="field.disabled"
    />
    <el-select
      v-else-if="field.type === 'select'"
      v-model="localForm[field.prop]"
    >
      <el-option
        v-for="opt in field.options"
        :key="opt.value"
        :label="opt.label"
        :value="opt.value"
      />
    </el-select>
    <!-- 更多 type 分支 -->
  </el-form-item>
  <el-form-item
    v-else
    :key="field.prop"
    :label="field.label"
  >
    <slot :name="field.prop" :value="localForm[field.prop]" />
  </el-form-item>
</template>

表单组件的核心逻辑

弹窗打开时，如果是编辑模式要把 formData 深拷贝到内部 localForm，防止直接修改 prop 导致父组件数据意外变更。关闭时重置 localForm 为空对象，同时调用 el-form.resetFields() 清掉校验状态。

watch: {
  visible(val) {
    if (val) {
      this.localForm = JSON.parse(JSON.stringify(this.formData || {}));
      this.$nextTick(() => {
        if (this.$refs.form) this.$refs.form.clearValidate();
      });
    }
  },
  mode() {
    // 切换模式时重置表单
    this.localForm = {};
  }
},

methods: {
  handleSubmit() {
    this.$refs.form.validate(valid => {
      if (!valid) return;
      this.$emit('submit', {
        mode: this.mode,
        data: JSON.parse(JSON.stringify(this.localForm))
      });
    });
  },
  handleClose() {
    this.localForm = {};
    this.$refs.form.resetFields();
    this.$emit('update:visible', false);
  }
}

父组件使用的时候，只需要传 fields 配置和处理 submit 事件：

<form-dialog
  :visible.sync="dialogVisible"
  :mode="dialogMode"
  :fields="userFields"
  :form-data="currentUser"
  @submit="onUserSubmit"
/>
data() {
  return {
    userFields: [
      { prop: 'userName', label: '用户名', type: 'input',
        rules: [{ required: true, message: '必填' }] },
      { prop: 'role', label: '角色', type: 'select',
        options: [{ label: '管理员', value: 'admin' },
                   { label: '编辑', value: 'editor' }] },
      { prop: 'status', label: '状态', type: 'switch' }
    ]
  };
}

八套表单缩减到一套组件，字段用 JSON 配置描述。改表单行为只改组件内部一处理，全局生效。新增模块只需要写 fields 数组，页面代码从 ~250 行降到 ~80 行。

表格封装：保持一致性和权限控制

跟表单的问题类似：每个后台列表页一张 el-table，列定义、分页、多选、操作栏全在模板里重复。更麻烦的是权限控制——管理员能看到操作列里的"删除"按钮，普通编辑不能。之前权限判断散落在每个页面的 v-if 里，检查起来费劲。

封装的思路：列配置数组传给组件，操作列单独用一个 actions prop，每个 action 带 permission 字段，组件内部全局过滤：

props: {
  columns: Array,
  data: Array,
  loading: Boolean,
  pagination: Object,
  actions: {
    type: Array,
    default: () => []
    // 每项: { label, type, permission, handler }
  }
},

computed: {
  visibleActions() {
    const permissions = this.$store.state.user.permissions || [];
    return this.actions.filter(
      a => !a.permission || permissions.includes(a.permission)
    );
  }
}

使用方代码变得极简：

<data-table
  :columns="columns"
  :data="list"
  :loading="loading"
  :pagination="pagination"
  :actions="tableActions"
  @page-change="onPageChange"
  @action="onAction"
/>
tableActions: [
  { label: '编辑', type: 'primary', action: 'edit',
    permission: 'user:update' },
  { label: '删除', type: 'danger', action: 'delete',
    permission: 'user:delete' }
]

权限配置集中在 Vuex 的 user module 里维护，接口返回权限列表后存 store。表格组件从 store 读，不做独立请求——省 N 次不必要的权限接口调用。

搜索栏的递进式封装

后台列表大多带搜索栏。八个列表页的搜索栏结构各不相同但交互模式一致：若干筛选项 + 搜索按钮 + 重置按钮，按钮触发时可能是回车也可能是点击。

抽一个 SearchBar 组件，props 收 filters 数组（和表单 fields 结构类似），点击搜索 emit search 事件带出所有筛选值。这样列表页面结构稳定成三段：

<search-bar :filters="searchFilters" @search="onSearch" />
<data-table :columns="columns" :data="list" :actions="actions" />
<form-dialog :visible.sync="visible" :fields="formFields" @submit="onSubmit" />

一个后台模块的基础骨架就这么固定下来。新增模块只需要提供三组配置：searchFilters、columns、formFields，以及对应的 API 调用方法。开发效率从两天一个模块提速到半天。

Element UI 2.4 当时刚出稳定版，iView 是主要竞品，我选 Element 的原因是表单校验 async-validator 集成更丝滑、table 的 fixed 列支持也更成熟。这套封装方案在三个后台项目里跑了大半年，后面只是随着业务新增了一些 field type，组件本体几乎没有大改。
